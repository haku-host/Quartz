Здесь показана настройка **собственного домена** у вашего DNS-провайдера. Если имя ещё не куплено или нужно настроить Cloudflare и NS у регистратора, начните с [[help/custom-domain|полного руководства по внешнему домену]]. Для поддомена из зон Haku Host есть [[billing/domains|настройка в биллинге]].

## Сначала проверьте прямой адрес

Убедитесь, что сервер запускается и принимает подключение по паре адрес:порт из [[pterodactyl/network|Pterodactyl]] или по адресу настроенного Minecraft-сервера на [[hakustack/network|VDS]]. Используйте игровой порт, а не порт SFTP или веб-панели.

Если панель показывает имя ноды, узнайте его IPv4 через `nslookup имя-ноды-из-панели`. Из строки подключения уберите `:порт` перед DNS-запросом. Берите IP из ответа для этой ноды; строка `Server` в выводе обозначает ваш DNS-сервер. При нескольких адресах или сомнениях уточните адрес услуги у поддержки.

DNS настраивается в зоне, на которую указывают **NS вашего домена**. Если делегация уже переведена в Cloudflare, записи нужно менять там.

## A: домен с явно указанным портом

В зоне `example.com` создайте **A** с именем `play` и реальным IPv4 игровой услуги. В поле адреса не добавляйте порт, `http://` или путь. TTL можно оставить предложенным панелью.

После обновления DNS подключение по `play.example.com:порт` должно вести на тот же сервер. Если этого достаточно, SRV можно не создавать.

В Cloudflare у A-записей игрового имени и целевого узла установите **DNS only** — серую тучку. Обычный режим **Proxied** предназначен для HTTP-трафика и не заменяет игровой прокси. Подробности — в [справке Cloudflare](https://developers.cloudflare.com/dns/proxy-status/).

## SRV для Minecraft Java

SRV позволяет Java-клиенту найти узел и игровой порт. Для адреса **`play.example.com` без порта**:

1. Оставьте A-запись `play`, созданную выше.
2. Создайте ещё одну **A**: имя `node`, значение — тот же IPv4 игровой услуги, режим **DNS only**. Получится `node.example.com`.
3. Добавьте **SRV** со следующими полями:

| Поле       | Пример                                      |
| ---------- | ------------------------------------------- |
| Тип        | SRV                                         |
| Имя записи | `_minecraft._tcp.play` в зоне `example.com` |
| Приоритет  | `0`                                         |
| Вес        | `0`                                         |
| Порт       | Реальный порт из панели                     |
| Цель       | `node.example.com`                          |

В поле **«Цель / Target»** впишите полное `node.example.com`. Этот узел должен иметь собственную запись A; CNAME в качестве цели SRV не используйте. В цель не вписываются IP, URL или `имя:порт`. Это требование формата [SRV в RFC 2782](https://www.rfc-editor.org/rfc/rfc2782).

Если DNS-панель разделяет поля, заполните **Service** = `_minecraft`, **Protocol** = `_tcp`, **Name** = `play`. Если поле имени одно, введите `_minecraft._tcp.play`. Проверьте итоговое полное имя: **`_minecraft._tcp.play.example.com`**. Панели, ожидающие полное имя, принимают его целиком; доменная зона не должна повториться дважды.

Сохраните запись и в Java-клиенте укажите **`play.example.com` без `:порт`**. Порт в SRV должен совпадать с назначенным серверу; менять порт сервера ради DNS не требуется.

Назначение полей A и SRV описано в [справке DNS](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/).

_Имена в зоне example.com — примеры. В своих записях используйте домен, IP и порт вашей услуги._

## Проверка

Проверьте записи с компьютера игрока, заменив имена своими:

```sh
nslookup -type=A node.example.com
nslookup -type=SRV _minecraft._tcp.play.example.com
```

Первый запрос должен вернуть IPv4 игрового сервера, второй — цель `node.example.com`, нужный порт, приоритет и вес. `NXDOMAIN` у SRV обычно означает, что такой записи не видно: проверьте имя с `_minecraft._tcp`, нужную DNS-зону и кэш. Команда `nslookup` описана в [справке Microsoft](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/nslookup).

После обновления DNS-кэша проверьте вход в Java-клиенте без порта. Если прямой адрес работает, а домен нет, сопоставьте цель и порт SRV с панелью. Проверьте **DNS only** и отсутствие ошибочной AAAA-записи. После смены IP или игрового порта обновите соответствующие A и SRV.

## Подключение по корню домена

Для входа по **`example.com`** вместо `play.example.com` используйте ту же A-запись `node.example.com`, но имя SRV должно быть **`_minecraft._tcp`** в зоне `example.com`. Её полное имя получится **`_minecraft._tcp.example.com`**; цель и порт остаются прежними.

В панели с отдельными полями это **Service** = `_minecraft`, **Protocol** = `_tcp`, **Name** = `@` или пустое поле — по правилам провайдера. Итоговое имя проверяйте после сохранения: вариант `_minecraft._tcp.@.example.com` неверен.

Если корневой домен выделен только для игры, создайте для него также **A** с именем `@` и IPv4 игровой услуги. Если на `example.com` уже работает сайт, удобнее отвести игре `play.example.com`: тогда существующие записи сайта остаются самостоятельными.

Проверка корневого варианта:

```sh
nslookup -type=SRV _minecraft._tcp.example.com
```

## Minecraft Bedrock и другие игры

Запись `_minecraft._tcp` предназначена для Minecraft Java. Для Bedrock используйте A-запись и укажите в поддерживающем это клиенте **домен и игровой порт отдельными полями**. Для других игр сверяйтесь с возможностями их клиента: наличие SRV само по себе не заставляет приложение её читать.
